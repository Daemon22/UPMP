# UPMP Process Observatory

This self-contained visual concept explores UPMP as a layered process observatory. It starts with a system-scale river map, then lets you enter subsystems and selected child processes without laying every detail across one crowded screen. The supplied sapphire-and-gold brand artwork anchors the interface.

## Open and explore

Open `index.html` in a modern desktop browser. No install or network connection is required.

- **River map** starts at the full ecosystem: intent and entry, orchestration, parallel workstreams, evidence, assurance, and outcomes.
- Select a stream to inspect its expected behavior, actual progress, checkpoint results, evidence, deviations, and mutation links. Double-click it or choose **Enter this process** to open its branches.
- Follow deeper lanes such as retry and recovery, integration schema validation, evidence provenance, mutation impact, and button lineage. Breadcrumbs and the zoom-out control return to parent processes.
- **Architecture** groups the proposed services into orchestration, execution, evidence/event, and assurance planes. Select a service card to open its process lane.
- **Activity**, **Mutations**, and **Output surfaces** show run events, expected-versus-actual changes, and user-facing results.
- Choose **Open simple example** to switch to the original face-verification journey. Its button can still be traced from product intent through component, action binding, workflow, and result state.

The default page remains an illustrative design. `live.html` is the first runtime-connected view: it reads an UPMP process-run snapshot, opens declared process groups progressively, shows verified checkpoint progress, and draws only workflow dependencies and transitions that are present in the run graph.

## View a live UPMP run

From the repository root, start the instrumented demonstration:

```bash
python examples/live_process_observatory.py
```

Open the local address printed in the terminal. The page refreshes from the current JSON snapshot while the example workflow runs. Its step values are generated by the executable UPMP workflow; they are not hardcoded dashboard metrics. The example uses a four-step record preparation and release process and keeps the local viewer open after the run completes.

Applications can use the same pieces directly:

1. Define an immutable `ProcessCharter` with the goal, acceptance policy, and nested `ProcessPart` hierarchy.
2. Create a `ProcessRunTracker` with the charter, workflow steps, initial state, and snapshot path.
3. Pass it as `audit_sink` and pass `charter.audit_metadata` as `audit_metadata` to the sequential or parallel orchestrator.
4. Call `tracker.begin()` before execution and `tracker.finish(result)` after the orchestrator returns.
5. Provide the snapshot path and prototype UI directory to `make_observatory_server`; its read-only endpoint is `GET /api/process-run` and its home page is `live.html`.

Progress counts passing precondition and postcondition checks. A process run completing is separate from its goal passing. A mutation is shown only when an adapter records it with `tracker.record_mutation(...)`; deviations also include observed failed or indeterminate checks, failed or denied actions, skipped steps, and explicit adapter reports. Supply an existing UPMP audit sink through `downstream_sinks` when the application requires durable, hash-chained event storage.

## Files

- `index.html` is the interactive prototype.
- `assets/` contains the supplied brand artwork adapted for the interface.
- `previews/` contains static visual plates used in the concept PDF.
- `render_previews.py` recreates the static visual plates.
- `assemble_pdf.py` rebuilds the PDF with both the original simple views and the complex ecosystem views.
